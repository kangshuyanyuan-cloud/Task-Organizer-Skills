作業の終わりに、今回の内容を記録に残す。
次に作業を始めるとき（`work-start`）に「どこまで進んで、何が残っているか」がすぐ分かるようにするためのスキル。

## 前提（自分の環境に合わせて書き換える）

| 項目 | 例 | 説明 |
|---|---|---|
| 作業ログの置き場所 | `作業ログ/` | `YYYY-MM-DD.md` で書く。同じ日は追記 |
| ステータスファイル | `STATUS.md` | 進行中の作業と「次にやること」 |
| Gitリポジトリ | `.`（いまのフォルダ） | Gitを使っていなければ手順4を飛ばす |
| pushするブランチ | `main` | チームの決まりに合わせる |

## 手順

### 1. 日付と時刻を確かめる

```bash
date +%Y-%m-%d
date +%H:%M
```

会話の中の日付ではなく、パソコンの時刻を使う。

### 2. 今回の作業をまとめる

この作業で実際にやったこと（作ったファイル・直したもの・実行したこと・決まったこと・終わっていないこと）を、短い箇条書きにする。専門用語は使いすぎない。

### 3. 作業ログを書く

`作業ログ/<YYYY-MM-DD>.md` が**無ければ新しく作り、あれば末尾に追記する**（前の内容は消さない）。

```markdown
# 作業ログ <YYYY-MM-DD>

## <HH:MM> セッション
**やったこと**
- ...

**決まったこと**
- ...

**次にやること / 終わっていないこと**
- ...
```

あわせてステータスファイルを更新する。

- 進行中の作業の「状態」と「次にやること」を最新にする（終わったものは反映、新しく残ったものは追加）
- つまずいた点・次に同じ失敗をしないための注意があれば書き足す（前の項目は消さない）
- 大事な決定があれば、日付・決定・理由を1行で残す

### 4. Gitの状態を確認してから、コミット・pushする

チームで同じリポジトリを触っている場合、自分の作業中に他の人が変更を足していることがある。
**pushする前に必ず確認する**（弾かれてから対応するのではなく、押す前に見る）。

```bash
git fetch
git status -sb                         # いまのブランチと、未コミットの変更
git log --oneline HEAD..origin/main    # 他の人の新しいコミット
```

- 他の人のコミットがあれば、**先に取り込む**（`git pull --rebase origin main`）
  - 取り込んだら、テストや動作確認をやり直す（相手の変更で壊れていないか）
  - 同じファイルを触っていたら、どちらかを勝手に捨てず、差分を読んでから合わせる
- 作業ログ・ステータスファイル以外の変更が混ざっていたら、中身を確認してから含めるか決める
  （分からない変更は勝手に退避・破棄せず、報告する）

```bash
git checkout main
git add 作業ログ/<YYYY-MM-DD>.md STATUS.md
git commit -m "docs: 作業ログ <YYYY-MM-DD>"
git push origin main
```

- 差分が無くてコミットされなかった場合は、その旨だけ伝える
- pushが認証などで失敗したら、エラー内容をそのまま伝える（認証情報は触らない）

### 5. 完了の報告

- 作成・追記したファイルの場所
- コミットの番号（短いもの）と、pushしたブランチ
- 他の人の変更を取り込んだ場合は、その内容と確認したこと
- 次にやること（作業ログに書いたもの）

## 守ること

- 作業ログは箇条書き中心で、あとから読んで分かる言葉で書く
- 記録は消さずに足していく
