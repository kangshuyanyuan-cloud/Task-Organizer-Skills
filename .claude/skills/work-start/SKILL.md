作業を始めるときに、**いきなり手を動かさない**。
これまでの記録を読み直して「今日やること」を表にまとめ、**確認を取ってから**作業に入る。
前回どこまで進んだか・何が残っているか・他の人が何を変えたかを、最初に整理するためのスキル。

## 先に読むもの

このスキルを置いた `.claude` フォルダの `shared/` にある2つを読む
（このファイルから見て `../../shared/`）。

| ファイル | 中身 |
|---|---|
| `前提.md` | 記録の置き場所・Gitの使い方。以下の「ステータスファイル」などはここの値を指す |
| `やることリストの型.md` | 表の形・優先順位のつけ方・保存のしかた・確認の取り方 |

## はじめて使うとき（記録がまだ無い）

ステータスファイルも作業ログも無いときは、読むものが無いので、代わりに次のようにする。

1. 「記録がまだ無いので、いま抱えている作業を教えてください」と聞き、
   作業名・期限・誰のためか・どこまで進んでいるかを**まとめて一度に**答えてもらう
2. その答えから、手順4〜5と同じ形で今日やることの表を作る
3. 確認が取れたら、ステータスファイルを `shared/見本/STATUS.md` の形で作り、答えてもらった内容を書き込む

作業ログは作業の終わりに `work-end` が作るので、ここでは作らない。
2回目からは下の手順どおりに進む。

## 手順

### 1. 記録を読む

| 読むもの | 何を取るか |
|---|---|
| ステータスファイル | 進行中の作業と「次にやること」 |
| 作業ログの最新2本（ファイル名の日付が新しい順） | 前回やったこと、途中で止まったこと、つまずいた点 |
| 前回のやることリスト | 下の「繰り越し方」 |

ファイル名だけで判断せず、**中身を開いて読む**。

**前回のやることリストの繰り越し方**

- ファイル名の日付が一番新しいものを開き、その中の**すべての見出しの表**を見る
  （同じ日に作業開始と会議の表が追記されていることがあるため。一番下だけ見ると前の表の残りが抜ける）
- 状態が `済` 以外の行を、**そのまま今日の表に繰り越す**（消さない）
- 同じ作業が複数の表に出ていたら、下にある（新しい）表の状態を使い、1行にまとめる
- ステータスファイルや作業ログで終わったと分かるものは、`済` として扱い繰り越さない
- 見出しの下が `状態：未確認` のまま終わっている表は、確認されなかった案なので、行ごとに今も必要か見直してから入れる

### 2. 新着を確かめる

新着を見るフォルダ（`前提.md` で「なし」なら飛ばす）の、7日以内に置かれたファイルを見る。

- 文字起こしらしいファイルは、`やることリスト/` の**すべてのファイル**の見出しを探し、そのファイル名が**まだ出ていないものだけ** `meeting-todo` の手順で扱う（出ていれば処理済み）
- 資料は、今日の作業に関係しそうなら開いて読む

### 3. Gitの状態を確かめる

`前提.md` で「Gitを使うか」が「使わない」なら飛ばす。

チームで同じリポジトリ（＝ファイルの変更履歴をためておく場所）を使っていると、
自分がいない間に他の人が変更を足していることがある。それを知らずに今日の予定を立てないよう、最初に確かめる。

```bash
git remote                             # 共有先（リモート）があるか。何も出なければ下の fetch 以降は飛ばす
git fetch                              # 共有先の最新の情報を取ってくる（手元のファイルは変わらない）
git status -sb                         # いまのブランチと、まだ記録していない変更
git log --oneline HEAD..@{u}           # 他の人の新しい変更（手元にまだ無いもの）
git log --oneline @{u}..HEAD           # 自分の、まだ共有先に送っていない変更
```

`@{u}` は「いまのブランチが追いかけている共有先のブランチ」のこと。設定が無いと失敗するので、そのときは `origin/<作業ブランチ>` に読み替える。

見つかったものは、やることリストの材料にする。

| 見つかったもの | リストでの扱い |
|---|---|
| 他の人の新しい変更 | 「変更を取り込む」を上のほうに入れる。`git log -p HEAD..@{u}` で中身を読み、今日触るファイルと重なるならかんたん説明に書く |
| 自分の、まだ送っていない変更 | 「前回の分を送る（push）」を入れる。ただし `前提.md` で「記録をpushするか」が「しない」で、送っていないのが記録のコミット（`docs: 作業ログ …`）だけなら入れない |
| まだ記録していない変更 | 中身を見て、前回の途中作業なら繰り越しに入れる。何の変更か分からないものは「確認したいこと」に回す（勝手に消さない・記録しない） |
| いまのブランチが作業ブランチと違う | 「確認したいこと」に入れる（ブランチは勝手に切り替えない） |
| fetch が失敗した | 「他の人の変更は未確認」と表の下に書く |

この時点では取り込み（`git pull`）をしない。取り込みは、確認が取れたあとのタスクとして行う。

### 4. 今日やることを組み立てる

- 繰り越し分＋記録から読み取った宿題＋新着からの依頼＋Gitの状態 を、ひとつの表にまとめる
- **期限が過ぎているものは先頭に置き、「期限切れ」と書く**
- 相手の返事待ちのものは、状態を `待ち（相手の名前）` にする
- 1日で終わる量を超えていたら、**今日やる分と今日はやらない分を線で分ける**

### 5. 表を出して、確認を取る

`やることリストの型.md` の「表の形」「確認したいことは、最初にまとめて出す」「保存のしかた」「出したあとの動き」に従う。

- 表 → 進め方と完了条件 → 確認したいこと → 仮に決めたこと の順で出す
- 見出しは `## HH:MM（作業開始）` にして保存する
- **確認が取れるまで、表の作業には手を付けない**

### 6. 確認が取れたら

- 見出しの下を `状態：確認済み（HH:MM）` に書き換える
- 担当が `Claude` の行を上から進め、1件終わるごとに「状態」列を更新する
- 作業の終わりは `work-end` で記録を残す

## 守ること

- 表と箇条書きで整理する
- 記録に無いことを推測で書かない。分からないことは「確認したいこと」に回す
